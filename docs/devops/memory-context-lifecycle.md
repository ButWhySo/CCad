# CCad Agent context and memory lifecycle

This note describes the request assembly and memory behavior implemented in Sprint 967 and the semantic conversation-history compaction added in Sprint 970. Whenever estimated request size crosses the configured large-context threshold, CCad sends the user a detailed end-to-end explanation of these stages plus safe counts and estimates. Diagnostics never expose prompts, design payloads, stored memory text, provider credentials, or raw tool arguments.

The chat command `/context [draft]` runs that same bounded accounting locally on demand. With a draft, it retrieves memory against that draft and counts it as a hypothetical user message; without one, it counts the current bounded conversation. It renders a complete breakdown in the chat stream even below the automatic threshold, and labels the result as a local preview for which no provider request was sent. It does not invoke the graph/model, run tools, add the command or draft to conversation history, or export draft/content text. The `provider_request_context` event and optional `CCAD_TRACE_DEBUG` stderr diagnostic carry safe count/identity metadata only; the visible explanation likewise contains counts and lifecycle metadata, not source content. `CCAD_AGENT_LARGE_CONTEXT_TOKENS` controls the automatic large-context threshold (default 4096 estimated input tokens; a minimum 512); the GUI harness lowers it only for its scoped validation process.

The visible preview is divided into request components, per-tier memory state, ranking/omissions, assembly lifecycle, project envelope, and privacy boundary. Each tier reports whether it is enabled, how many records are cached in this process, retrieved for this request, and durably stored. Development diagnostic JSON is forwarded to the Qt process log rather than rendered as a backend warning. On the Sprint 969 live UI-map run, the actual catalog contributed 59 tool schemas and the active project snapshot contributed 19,862 source characters; the total estimated input was 12,142 tokens. The child process remained provider-uninitialized for explicit runtime validation, and the GUI event reported `provider_request_sent:false`.

## Provider request assembly

Before a chat turn, the Qt Agent panel sends the user text, durable session ID, LangGraph thread ID, and current project context to the Python child process. Session binding also updates those identities before the first model request. The Python runtime selects the persisted provider/model and credential independently; credentials remain in the OS vault/process boundary and do not enter the context package.

The runtime configures enabled memory tiers for the current identities, retrieves up to eight matching records by query-term overlap, recency, and tier order, then constructs a versioned JSON envelope containing the project snapshot, selected memories, a conversation-message count, and mutation/secret policy. STM belongs to a task scope started explicitly with `/task start`, inspected with `/task status`, and ended with `/task end`; without an active scope, the current turn receives an isolated, non-retained STM identity. The chat command palette and `/commands`/`/help` expose these controls. Ending or replacing a task clears its process-only STM records. The conversation itself is sent separately as provider messages, not duplicated in this envelope. Tool schemas are bound separately to the selected model. Past tool-call payloads and multimodal blocks are counted where possible; unsupported multimodal payload sizes are reported as unestimated.

When the estimated request crosses its configured threshold, the explanation identifies the system prompt, project snapshot or summary, retrieved memory, conversation history, tool schemas, and any counted tool or multimodal payloads. It reports inclusion, truncation, omission, and source counts, as well as memory enabled/loaded/persistent/retrieved counts and ranking provenance. Its estimate is `ceil(text characters / 4) + 4 tokens per message + 8 tokens per tool`, not provider tokenizer output. The explanation appears before provider execution so quota errors do not hide it. It does not disclose the corresponding content. The exact request's safe identity includes package digest and context revision, and `provider_request_sent` distinguishes a local preview/no-op from a real call.

The budget report measures system instructions, project snapshot or summary, retrieved memories, envelope overhead, conversation messages, prior tool-call payloads, and bound tool schemas. Token counts use the explicit estimate `ceil(text characters / 4) + 4 tokens per message + 8 tokens per tool`; this is not a provider tokenizer. A selected-model context limit is shown only when current authoritative model metadata supplies it. At the configured large-context threshold, the Agent explains these sources, memory state, retrieval ranking, overflow omissions, truncation, and the model-limit uncertainty without including their contents. `CCAD_TRACE_DEBUG` writes the same safe counts and status to development stderr.

The project envelope has a character bound. If its full snapshot does not fit, the builder substitutes a valid counts-and-revision summary, then removes lower-ranked memories until the JSON is within budget. Exact included and omitted memory counts, source character counts, package digest, and context revision accompany the request. If even the safe summary does not fit, the request fails before provider execution instead of sending malformed or partial JSON.

## Memory tiers

All tiers use one local, atomic JSON store at `%APPDATA%/CCad/agent_memory.json` (or `CCAD_AGENT_MEMORY_PATH` when explicitly configured), but have distinct namespace and lifetime rules. Short-term memory uses a task UUID generated by the Python runtime; `/task start` holds that identity across turns for one durable Agent session, and `/task end` clears it. Starting a replacement task also clears the prior STM scope. Turns without an active task receive fresh, non-retained IDs; adding STM in that state is rejected rather than silently creating memory that cannot be retrieved later. STM is process-memory-only, isolated by task, and is discarded when disabled or when the process exits. At most 32 active session/task scopes and 64 records per task are retained; least-recently-used task scopes are cleared when the cap is reached. Conversation memory is durable and keyed by the LangGraph thread ID. Episodic memory is durable and keyed to the local OS user's CCad memory store, so it can be retrieved across that user's projects on this device. Project ID is not used to split episodic storage.

Enabling a tier loads its current namespace into a bounded runtime cache. Disabling it immediately empties that cache and prevents retrieval, add, and update through the manager; durable records remain untouched. Explicit list and delete operations remain available for managing stored records. A tier switch unloads the previous identity before loading the new one. Each toggle returns a snapshot of all tiers, so Personalisation shows enabled state plus runtime and persistent record counts together; `Manage memories` uses the same typed IPC and tier manager as `/memory` commands.

Scope labels are retained as record metadata and can be used for explicit list/delete filters. Retrieval isolation is enforced by tier and namespace; scope labels are not semantic retrieval filters. Defaults are `task` for short-term, `conversation` for LTM, and `user` for episodic records. Memory capture is explicit through `Manage memories` or `/memory add`; ordinary conversation is not automatically learned or persisted.

Writes reject secret-like content or metadata, including common API-token prefixes and bearer values. Legacy secret-bearing records are excluded from runtime retrieval and the Manage Memories listing; reset remains available to remove them. Expiry values must be timezone-aware ISO-8601 timestamps and expired records are removed on load or retrieval. Normalized exact duplicates resolve to the existing entry. Adds and updates reject high lexical-overlap near-duplicates within the same tier and namespace, identifying the existing record so users can update it deliberately. The detector requires at least five distinct terms and Jaccard overlap of at least 0.88; this is lexical similarity detection, not a claim of semantic equivalence. Durable namespaces retain the newest 64 records; STM caches retain 64 per task, across at most 32 tasks. This bounded retention is not semantic summarization; semantic compaction remains open work.

`/memory list`, `add`, `update`, `delete`, and `clear` route through `MemoryManager`; they no longer write directly to `MemoryStore`. A clear by scope only affects matching namespaces, while clear all/reset removes durable records across namespaces. The Settings reset action and individual record deletion require an explicit confirmation. Disabling a tier is not deletion and does not clear chat transcripts or LangGraph checkpoints.

Enabling LTM or episodic memory first opens the durable JSON file, validates its records, creates an empty store if it does not exist, and loads the selected tier namespace before setting the runtime enabled flag. Corrupt JSON is not treated as an empty store and is never overwritten by activation or a later add. An unavailable or corrupt store reports a safe category, unloads the affected process cache, disables retrieval, and renders the persistent count as unknown (`?`). Memory preference changes use a verified atomic configuration write before activation; failed activation attempts to restore the prior saved preference. `memory_state` returns both persistence and runtime state so Settings can display what actually happened.

Sprint 971 validates those guarantees through a real offline orchestrator subprocess using a disposable user profile, memory file, checkpoint DB, and project sentinel. It toggles LTM and episodic tiers, verifies LTM records and checkpoint data survive disablement, refuses reset without confirmation, performs confirmed reset only on the test namespace, and preserves malformed memory-file bytes. The app-owned GUI-map scenario exercises settings toggles, manage-memory input, title/scope/content save, and the reset confirmation's cancel button without touching the user's profile. It closes and reopens Settings, navigates back to Personalisation, and checks visible toggles against their original state and persisted configuration; the earlier mismatch was a test targeting error because those controls are hidden on the default General page. The Release build and full CTest passed 104/104, targeted Pyright returned zero diagnostics, and all 42 generated screenshots plus stdout/stderr were inspected. Durable memory semantic compaction remains unimplemented and separate from chat-history `/cc` compaction.

The `/cc` and `/compact` commands apply only to conversation history. They serialize bounded older turns while retaining the latest four original messages, omit unsafe or non-text content and tool arguments, and ask the selected model for a concise recap with tools disabled. The recap is bounded, checked for secrets/instruction-like content, and rejected unless it is shorter than its source. A successful recap replaces older messages in the actual LangGraph checkpoint and is read back for verification; a failed update attempts restoration and reports recovery failure distinctly. Pending graph work is not compacted. The user is told before the provider request that bounded conversation text will be sent and may consume quota; reports distinguish prepared, sent, complete, and failed states. This operation does not compact durable memory records.

## Verification boundary and remaining limitations

Offline tests exercise store CRUD, namespace isolation, runtime unloading, tier gating, persistent metadata preservation, expiry, secret rejection, duplicate handling, retention, reset, and slash-command operations. The Sprint 967 Release/CTest gate passed 98/98; its Settings/Manage Memories GUI-map pass performed ten mapped actions per pass, with all 26 screenshots and captured stdout/stderr inspected. Sprint 969 added and verified the provider-free large-context chat preview: Release build succeeded, full CTest passed 100/100, targeted Pyright reports zero diagnostics, and the app-owned GUI-map flow completed eight mapped interactions with all nine screenshots and logs inspected. No provider request was sent for this proof. clangd's source check timed out without diagnostics and remains an explicit validation limitation.

STM task IDs persist only while a `/task` scope remains active for that session; unstaged turns each receive a fresh task ID. The bounded in-process STM cache does not survive application restart. Episodic storage is local-user scoped, not synchronized across devices. Memory is not automatically captured from ordinary chat. Semantic compaction for durable memory records is not implemented; only conversation history has provider-backed semantic compaction. These are deliberate visible limitations, not claims of completed behavior.
