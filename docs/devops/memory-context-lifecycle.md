# CCad Agent context and memory lifecycle

This note describes the request assembly and memory behavior implemented in Sprint 967. When estimated request size crosses the configured large-context threshold, CCad sends the user a detailed explanation of these stages plus safe counts and estimates. Diagnostics never expose prompts, design payloads, stored memory text, provider credentials, or raw tool arguments.

## Provider request assembly

Before a chat turn, the Qt Agent panel sends the user text, durable session ID, LangGraph thread ID, and current project context to the Python child process. Session binding also updates those identities before the first model request. The Python runtime selects the persisted provider/model and credential independently; credentials remain in the OS vault/process boundary and do not enter the context package.

The runtime configures enabled memory tiers for the current identities, retrieves up to eight matching records by query-term overlap, recency, and tier order, then constructs a versioned JSON envelope containing the project snapshot, selected memories, a conversation-message count, and mutation/secret policy. STM belongs to a task scope started explicitly with `/task start`, inspected with `/task status`, and ended with `/task end`; without an active scope, the current turn receives an isolated, non-retained STM identity. The chat command palette and `/commands`/`/help` expose these controls. Ending or replacing a task clears its process-only STM records. The conversation itself is sent separately as provider messages, not duplicated in this envelope. Tool schemas are bound separately to the selected model. Past tool-call payloads and multimodal blocks are counted where possible; unsupported multimodal payload sizes are reported as unestimated.

The budget report measures system instructions, project snapshot or summary, retrieved memories, envelope overhead, conversation messages, prior tool-call payloads, and bound tool schemas. Token counts use the explicit estimate `ceil(text characters / 4) + 4 tokens per message + 8 tokens per tool`; this is not a provider tokenizer. A selected-model context limit is shown only when current authoritative model metadata supplies it. At the configured large-context threshold, the Agent explains these sources, memory state, retrieval ranking, overflow omissions, truncation, and the model-limit uncertainty without including their contents. `CCAD_TRACE_DEBUG` writes the same safe counts and status to development stderr.

The project envelope has a character bound. If its full snapshot does not fit, the builder substitutes a valid counts-and-revision summary, then removes lower-ranked memories until the JSON is within budget. Exact included and omitted memory counts, source character counts, package digest, and context revision accompany the request. If even the safe summary does not fit, the request fails before provider execution instead of sending malformed or partial JSON.

## Memory tiers

All tiers use one local, atomic JSON store at `%APPDATA%/CCad/agent_memory.json` (or `CCAD_AGENT_MEMORY_PATH` when explicitly configured), but have distinct namespace and lifetime rules. Short-term memory uses a task UUID generated by the Python runtime; `/task start` holds that identity across turns for one durable Agent session, and `/task end` clears it. Starting a replacement task also clears the prior STM scope. Turns without an active task receive fresh, non-retained IDs; adding STM in that state is rejected rather than silently creating memory that cannot be retrieved later. STM is process-memory-only, isolated by task, and is discarded when disabled or when the process exits. At most 32 active session/task scopes and 64 records per task are retained; least-recently-used task scopes are cleared when the cap is reached. Conversation memory is durable and keyed by the LangGraph thread ID. Episodic memory is durable and keyed to the local OS user's CCad memory store, so it can be retrieved across that user's projects on this device. Project ID is not used to split episodic storage.

Enabling a tier loads its current namespace into a bounded runtime cache. Disabling it immediately empties that cache and prevents retrieval, add, and update through the manager; durable records remain untouched. Explicit list and delete operations remain available for managing stored records. A tier switch unloads the previous identity before loading the new one. Each toggle returns a snapshot of all tiers, so Personalisation shows enabled state plus runtime and persistent record counts together; `Manage memories` uses the same typed IPC and tier manager as `/memory` commands.

Scope labels are retained as record metadata and can be used for explicit list/delete filters. Retrieval isolation is enforced by tier and namespace; scope labels are not semantic retrieval filters. Defaults are `task` for short-term, `conversation` for LTM, and `user` for episodic records. Memory capture is explicit through `Manage memories` or `/memory add`; ordinary conversation is not automatically learned or persisted.

Writes reject secret-like content or metadata, including common API-token prefixes and bearer values. Legacy secret-bearing records are excluded from runtime retrieval and the Manage Memories listing; reset remains available to remove them. Expiry values must be timezone-aware ISO-8601 timestamps and expired records are removed on load or retrieval. Normalized exact duplicates resolve to the existing entry. Adds and updates reject high lexical-overlap near-duplicates within the same tier and namespace, identifying the existing record so users can update it deliberately. The detector requires at least five distinct terms and Jaccard overlap of at least 0.88; this is lexical similarity detection, not a claim of semantic equivalence. Durable namespaces retain the newest 64 records; STM caches retain 64 per task, across at most 32 tasks. This bounded retention is not semantic summarization; semantic compaction remains open work.

`/memory list`, `add`, `update`, `delete`, and `clear` route through `MemoryManager`; they no longer write directly to `MemoryStore`. A clear by scope only affects matching namespaces, while clear all/reset removes durable records across namespaces. The Settings reset action and individual record deletion require an explicit confirmation. Disabling a tier is not deletion and does not clear chat transcripts or LangGraph checkpoints.

## Verification boundary and remaining limitations

Offline tests exercise store CRUD, namespace isolation, runtime unloading, tier gating, persistent metadata preservation, expiry, secret rejection, duplicate handling, retention, reset, and slash-command operations. The Release build and full CTest gate passed 98/98. The Settings/Manage Memories GUI-map pass performed ten mapped actions per pass; all 26 screenshots were ingested and inspected, with captured stdout and stderr reviewed. This validates visible preference/tier controls and the memory manager's open/edit/close path. It does not prove a live provider-rendered large-context explanation, which remains opt-in and unchecked; no provider request was sent for this validation.

STM task IDs persist only while a `/task` scope remains active for that session; unstaged turns each receive a fresh task ID. The bounded in-process STM cache does not survive application restart. Episodic storage is local-user scoped, not synchronized across devices. Memory is not automatically captured from ordinary chat. Semantic compaction is not implemented. These are deliberate visible limitations, not claims of completed behavior.
